# Feature Specification: 浏览器书签双向同步插件

**Feature Branch**: `001-bookmark-sync`

**Created**: 2026-10-27

**Status**: Draft

**Input**: User description: "浏览器书签同步插件（Chrome 扩展，兼容 ego lite 等 Chromium 浏览器）。Chrome 与 ego 双向同步书签，最小版本为同机 Chrome ↔ ego lite，通过本机中继（127.0.0.1 本地服务）交换数据。同步语义必须是并集合并而非镜像覆盖：任一端新增的书签在同步后两端都保留；删除通过墓碑传播；支持文件夹结构、改名、移动；按逻辑身份键去重（chrome.bookmarks 的 ID 仅在本 Profile 内有效，不可跨浏览器使用）。ego 有多个 Profile，最小版本先支持指定单个 Profile。需处理同步回环（自己写入触发的事件不能再次回传）。"

> **2026-10-27 需求更新**：同步语义调整为**双向镜像**——两端最终保持完全一致；初始配对仍合并双方现有书签作为镜像基线；同一书签两端都改过时按到达顺序后到者胜（见 FR-006）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 两端新增的书签合并后都保留 (Priority: P1)

用户在 ego 上新增书签 A，又在 Chrome 上新增书签 B。同步完成后，两个浏览器里都必须同时看到 A 和 B，且每个书签只出现一次。

**Why this priority**: 这是用户明确提出的核心诉求。"合并"而不是"镜像覆盖"，决定了产品是否可用；只做这一条，已经能提供一个可验证的最小价值闭环。

**Independent Test**: 在两端安装扩展并完成配对后，分别在两个浏览器各添加一个书签，等待自动同步，检查两端书签集合是否一致且无重复。

**Acceptance Scenarios**:

1. **Given** 两端已配对且书签集合一致，**When** 在 ego 新增书签 A 并等待同步，**Then** Chrome 中出现 A，且只出现一次。
2. **Given** 两端已配对且书签集合一致，**When** 在 Chrome 新增书签 B 并等待同步，**Then** ego 中出现 B，且只出现一次。
3. **Given** ego 已新增 A、Chrome 已新增 B 且双方尚未同步，**When** 任意一端触发同步，**Then** 两端最终都包含 A 和 B，各一份。
4. **Given** 两端先后添加了标题与网址完全相同的书签，**When** 同步完成，**Then** 两端合并为一份，不产生重复项。

---

### User Story 2 - 删除会传播且不会复活 (Priority: P2)

用户在一端删除一个书签，同步后另一端也删除它；即使另一端曾短暂保留过该记录，也不会在后续同步中把它重新加回来。

**Why this priority**: 没有删除传播，书签会越同步越多，产品很快不可用。墓碑是"合并语义"不可缺少的另一半。

**Independent Test**: 在两端各放若干书签，完成一次同步后只在 Chrome 删除其中一个，观察 ego 是否删除，并连续执行多次同步确认它不再出现。

**Acceptance Scenarios**:

1. **Given** 两端存在同一书签，**When** 在 Chrome 删除并等待同步，**Then** ego 中该条书签消失。
2. **Given** 该书签已在 ego 消失，**When** 再次触发同步，**Then** 该条书签不会重新出现。
3. **Given** 在 ego 删除一个文件夹及其内容，**When** 同步完成，**Then** Chrome 中对应文件夹与内容一并消失，且不会复活。

---

### User Story 3 - 文件夹结构、改名和移动被保留 (Priority: P3)

用户在任意一端新建文件夹、把书签拖入文件夹、改名或移动文件夹，同步后另一端保持相同的层级、名称和归属。

**Why this priority**: 书签的价值很大程度取决于组织结构；只要结构丢失，用户仍需手工整理。

**Independent Test**: 在一端构造多层文件夹并放入书签，同步后在另一端逐层比对路径、名称与顺序。

**Acceptance Scenarios**:

1. **Given** 一端新建了嵌套文件夹并放入书签，**When** 同步完成，**Then** 另一端出现相同的文件夹层级与书签归属。
2. **Given** 一端重命名文件夹，**When** 同步完成，**Then** 另一端文件夹名称更新，书签不丢失。
3. **Given** 一端把书签从一个文件夹移动到另一个文件夹，**When** 同步完成，**Then** 另一端该书的归属位置同步变化，且不产生副本。
4. **Given** 一端修改书签的标题或网址，**When** 同步完成，**Then** 另一端跟随更新，且不产生"删除 + 新增"两条记录。

---

### User Story 4 - 同步状态可见、可控、可恢复 (Priority: P4)

用户能看到当前是否连接、上次同步时间、待同步数量与冲突提示，可以暂停/恢复同步或手动立即同步；同步服务断开期间的操作不会丢失。

**Why this priority**: 后台同步一旦不可见，用户无法判断数据是否安全；这是建立信任的必要能力，但不影响核心合并逻辑。

**Independent Test**: 停止同步服务、在两端各做修改、恢复服务，检查状态提示、补偿同步结果与是否有丢失或重复。

**Acceptance Scenarios**:

1. **Given** 同步服务未运行，**When** 打开扩展界面，**Then** 显示"未连接"并提供重试入口，浏览器书签功能不受影响。
2. **Given** 同步服务中断期间两端各有新增，**When** 服务恢复，**Then** 所有新增都被合并，无丢失、无重复。
3. **Given** 用户点击"暂停同步"，**When** 在两端继续编辑书签，**Then** 不会产生同步写入；点击"恢复"后变更被补齐。
4. **Given** 发生删除与修改冲突，**When** 查看同步记录，**Then** 能看到冲突条目及系统采取的处理结果。

---

### Edge Cases

- **两端同时修改同一条书签的标题**：以较晚的变更时间为准，任何一端的新增书签都不受影响。
- **一端删除、另一端在删除后刚改名或移动**：按到达顺序裁决——修改晚于删除则复活，删除晚于修改则删除；两种情况都在同步记录中标记冲突。
- **在已被另一端删除的文件夹中新增书签**：重建该文件夹，书签不丢失。
- **同一网址放在不同文件夹或使用不同标题**：视为不同书签，全部保留。
- **两端同时添加内容完全相同的书签**：合并为一条，不产生副本。
- **书签网址被编辑**：身份保持不变，不得表现为"删除旧书签 + 新增新书签"。
- **扩展自身写入触发变更事件**：不得把该事件当作远端变更回传，不得造成抖动、重复或无限循环。
- **ego 存在多个 Profile**：只有被选中的 Profile 参与同步，其他 Profile 的书签不得被读取或修改。
- **首次配对时两端已有大量不同书签**：全部并入，任何一方都不得覆盖另一方。
- **浏览器关闭期间另一端发生变更**：浏览器下次启动后补齐，且不产生重复。
- **书签规模达到万级**：同步过程不得阻塞浏览器界面操作。
- **同步服务地址被其他程序占用或不可达**：给出明确错误提示，不进行部分写入。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 以同一套浏览器扩展的形式在 Chrome 与 ego lite 中安装并运行。
- **FR-002**: 系统 MUST 在两端之间执行双向自动同步，并通过本机回环地址上的同步服务交换数据，不依赖云端账号。
- **FR-003**: 系统 MUST 采用并集合并语义；任一端新增的书签在同步后必须存在于另一端，同步过程不得删除或覆盖仅存在于另一端的书签。
- **FR-004**: 系统 MUST 为每个书签和文件夹建立与浏览器本地编号无关的跨端稳定身份；首次配对按"所在文件夹路径 + 标题 + 网址"匹配，之后身份在改名、移动、网址编辑时保持不变。
- **FR-005**: 系统 MUST 以墓碑记录传播删除；被删除的书签或文件夹不得因另一端仍存在而复活。
- **FR-006**: 当同一书签两端都发生修改（含一方删除、另一方改名或移动）时，系统 MUST 按到达顺序采用后到者胜：先删后改则复活，先改后删则删除；两端最终状态必须一致，并记录 `delete_vs_edit` 冲突。
- **FR-007**: 系统 MUST 保留文件夹的层级、名称和相对顺序；文件夹的新建、改名、移动、嵌套变化必须在另一端跟随。
- **FR-008**: 系统 MUST 将两端重复添加且内容一致的书签合并为一条；网址相同但文件夹或标题不同的书签视为不同条目，均保留。
- **FR-009**: 系统 MUST 抑制同步回环，自身写入引发的变更不得再次作为远端变更回传，不得造成重复、抖动或无限循环。
- **FR-010**: 系统 MUST 允许用户指定 ego 的一个 Profile 参与同步；未被选中的 Profile 不得被读取或写入。
- **FR-011**: 系统 MUST 在首次合并前生成两端书签快照以支持回滚，并在执行前展示将新增、合并、删除的条目数量供用户确认。
- **FR-012**: 系统 MUST 提供状态界面，展示连接状态、最近同步时间、待同步数量、冲突和错误信息。
- **FR-013**: 用户 MUST 能暂停/恢复同步并手动触发立即同步。
- **FR-014**: 当同步服务不可用时，系统 MUST 在本地暂存待同步变更，并在服务恢复后补偿同步，保证不丢失、不重复。
- **FR-015**: 同步范围 MUST 仅限书签与书签文件夹，不涉及历史记录、密码、标签页、扩展设置。
- **FR-016**: 同步操作 MUST 幂等，同一变更被重复应用时不得产生额外书签或文件夹。

### Key Entities *(include if feature involves data)*

- **书签**：表示一条网址收藏；关键属性包括标题、网址、所属文件夹、排序位置、跨端身份、创建与修改时间、状态（正常/已删除）。
- **文件夹**：表示书签的组织节点；关键属性包括名称、父文件夹、排序位置、跨端身份。
- **墓碑**：表示一次删除操作；记录被删除书签或文件夹的跨端身份、删除时间与来源端点，用于向其他端点传播删除并阻止复活。
- **同步端点**：参与同步的一个浏览器 Profile；最小版本包含 Chrome 的一个 Profile 与用户指定的 ego 一个 Profile。
- **同步记录**：一次同步的变更集合、执行结果与冲突列表，用于状态展示和问题追溯。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 两端各新增一个书签后，同步完成时两端书签集合内容一致，且每条书签恰好一份（重复率 0），验收场景通过率 100%。
- **SC-002**: 在一端删除书签后，另一端在 10 秒内完成删除，并且后续连续 10 次同步中不再出现该条书签。
- **SC-003**: 在一端改名、移动或调整文件夹后，另一端在 10 秒内呈现相同结果，归属错误率为 0。
- **SC-004**: 1,000 条书签、5 层嵌套文件夹的首次合并，在 60 秒内完成，合并后两端结构与内容一致率 100%。
- **SC-005**: 两端连续操作 1 小时并保持同步，书签总数不因同步产生额外副本（重复率 0），同步过程无回环抖动。
- **SC-006**: 同步服务中断 10 分钟后恢复，5 分钟内追平两端，书签丢失数为 0、重复数为 0。
- **SC-007**: 在所有验收与边界场景中，两端最终状态完全一致；除按镜像冲突规则明确判定的条目外，不产生非预期书签丢失。

## Assumptions

- Chrome 与 ego lite 运行在同一台电脑上；v1 不做跨设备同步，也不使用任何云账号。
- ego lite 允许为其指定 Profile 加载本扩展（2026-10-27 已在 0.6.0.16 实测通过：成功加载未上架 MV3 扩展，`bookmarks` 权限可用，读取到 170 个书签节点）；若未来版本失效，需改用文件桥接方案。
- ego 虽有多个 Profile，v1 只允许用户选择一个参与同步，其余 Profile 不受影响。
- 默认同步 `书签栏` 与 `其他书签` 两个根；移动端专用的 `synced` 根与不属于用户的系统节点不在 v1 范围内。
- 默认实时性为"两端在线时数秒内自动同步"，不承诺毫秒级一致。
- 书签规模按不超过 10,000 条设计；更大规模不作为 v1 验收目标。
- 用户接受本机有一个后台同步服务常驻运行；该服务仅监听回环地址。
- 冲突裁决以"两端最终一致"为最高优先级，按中继到达顺序后到者胜；删除晚于修改时会删除该书签，这是双向镜像的预期行为。
- 不包含：跨设备/云同步、书签全文搜索、书签去重清理工具、历史记录或密码同步。
